A track that will not play now says so, and tries the thing that usually fixes it. On the phone.

## The half hour of silence

There is one way extraction fails that produces no error anywhere.

A stream address from YouTube carries a signature, and Noctorium works that signature out using a copy of
YouTube's own player code. When that copy goes out of date — which happens on YouTube's schedule, not
ours — the signature it produces is *well formed and wrong*. Nothing throws. No field is missing. The
extraction looks perfect right up to the moment YouTube refuses the address, and by then the player is
holding it.

What made it worse is what happened next. The address went into the half-hour cache, so every later ask
for that track was answered from memory with the same dead address. And the player's own recovery —
drop the address, fetch a new one — asked an extractor that still had no idea its player code was
stale, so it produced the same dead address again. One stale player meant half an hour of a track that
would not start, with nothing in the log to say why.

Now, on the phone, a freshly extracted address is checked before it is trusted: one HEAD request, no
audio transferred. If YouTube refuses it, Noctorium throws away the cached player code and reads the
page again — which is the thing that actually fixes it. If it is refused a second time with a freshly
fetched player, that is not a stale signature any more, and you are told plainly rather than left with
a track that fails silently.

The check is deliberately reluctant to blame the address. Only an outright refusal counts. A rate
limit, a server having a moment, a lift with no signal, or a CDN that simply will not answer a HEAD all
mean "nothing was learned", and the track plays. A check that turns a bad moment into a refusal to play
is worse than no check at all.

**The desktop is unchanged.** It uses yt-dlp, which solves signatures afresh each time it runs and
updates itself independently of Noctorium, so it was never exposed to this.

## Everything else

Nothing. The player, themes, pinning, track edits, SponsorBlock skipping, accounts, scrobbling and both
installers are exactly as they were in 0.4.2. The desktop packages here are a rebuild of unchanged code.

## Which file

| Platform | File |
| --- | --- |
| Windows | `Noctorium-0.4.3-windows-x64-setup.exe`, or the `.msi` for deployment |
| Debian, Ubuntu, Mint | `noctorium_0.4.3_amd64.deb` |
| Fedora, RHEL, openSUSE | `noctorium-0.4.3.x86_64.rpm` |
| Android | `Noctorium-0.4.3.apk` |

Or take an installer and let it choose: `Noctorium-Installer-windows-x64.exe`,
`noctorium-installer-linux-x64`, `Noctorium-Installer-android.apk`. The desktop packages carry their own
Java runtime and their own Chromium for the sign-in window; the Windows ones carry mpv and yt-dlp as
well. **Close Noctorium before installing over it** — an installer cannot replace files a running
program holds open.
