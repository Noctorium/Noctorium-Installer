The installers, an updater that can finally see a release, and the artist's name back where it belongs.

## The installers

This is the first release that carries them. Two small programs whose only job is to put Noctorium on a
machine that has nothing on it yet.

| File | For | Size |
| --- | --- | --- |
| `Noctorium-Installer-windows-x64.exe` | Windows | 1.4 MB |
| `noctorium-installer-linux-x64` | Debian, Ubuntu, Mint, Fedora, RHEL, openSUSE | the same program, much the same size |
| `Noctorium-Installer-android.apk` | Android | 44 MB |

Each one asks GitHub what the latest release is, takes the single file that belongs on the machine it is
running on, checks it against the `SHA256SUMS.txt` published beside it, and hands it to whatever installs
software there. Windows runs the setup. Linux hands the `.deb` or `.rpm` to `apt` or `dnf` through a
`pkexec` prompt, so dependencies are resolved rather than merely reported. Android hands the APK to its
own package installer, which asks again itself — and the first time, sends you to a settings page to
allow installs from that source at all.

Neither will install something it could not check. A release with no `SHA256SUMS.txt`, or a download whose
hash does not match the one published for it, is deleted rather than run. Both skip their own files in a
release, so an installer never offers to install itself.

They fetch whichever release is latest **at the time they are run**, not this one, so an installer saved
today keeps working. The application's own updater takes over after that.

About the Android one's size: 44 MB to fetch a 17 MB APK is more than it ought to be. It is a Flutter
application built for every processor at once, and it can be made a third of that; it has not been yet.

## The updater is awake

0.4.0's notes said Noctorium's own updater would stay quiet until these repositories were public, because
GitHub answers 404 for the latest release of a private one and the application reads that as being up to
date. They are public now. Nothing changed in the updater — it simply gets an answer.

So a 0.4.0 installation finds this release by itself, at launch, without being told where to look. What it
downloads is checked against `SHA256SUMS.txt` from the same release before anything is run.

## The player bar shows the artist again

0.4.0 put the line being sung where the artist's name goes, while the lyrics were timed. It is gone on the
desktop and on the phone, along with the switch that turned it off, and the artist is back.

Lyrics themselves are untouched — the lyrics screen is unchanged, still timed, still following along. It
was only the player bar that borrowed the space.

A settings file written by 0.4.0 still mentions the switch. It is ignored rather than refused, so there is
nothing to do about it.

## And nothing else

This is 0.4.0 with one thing taken out and the installers added. Playback, themes, pinning, track edits,
SponsorBlock skipping, accounts and scrobbling are exactly as they were.

## Which file

| Platform | File |
| --- | --- |
| Windows | `Noctorium-0.4.1-windows-x64-setup.exe`, or the `.msi` for deployment |
| Debian, Ubuntu, Mint | `noctorium_0.4.1_amd64.deb` |
| Fedora, RHEL, openSUSE | `noctorium-0.4.1.x86_64.rpm` |
| Android | `Noctorium-0.4.1.apk` |

Or take an installer above and let it choose. The desktop packages carry their own Java runtime and their
own Chromium for the sign-in window; the Windows ones carry mpv and yt-dlp as well, so nothing has to be
fetched before the first track plays. **Close Noctorium before installing over it** — an installer cannot
replace files a running program holds open.

## Verifying a download

```
sha256sum --check --ignore-missing SHA256SUMS.txt
```

The APK is signed with the same release key as every version before it, certificate SHA-256 fingerprint:

```
46:CF:8B:96:C4:37:49:7A:93:AF:76:2B:91:94:AD:11:09:5D:D6:4A:B6:AB:EA:E9:60:C0:A5:98:C5:63:49:ED
```

A debug-signed build already on a phone has to be uninstalled first; Android will not replace it with a
release-signed one.
