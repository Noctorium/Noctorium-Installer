Tracks that start when you tap them, a repeat that does not reload, and a straight answer when the network is the problem.

## The wait after a tap

Measured on a phone before anything was changed: six and a half seconds from tapping a track to hearing it. Most of that was the track's page being read from YouTube — twice, once for the artist and length and once more for the audio — and the rest was the player filling a buffer bigger than it needed.

Now the page is read once, and what it says is kept for half an hour. The next track in the queue is looked up while the current one plays. The track at the front of *Where you left off* is looked up shortly after launch, on Wi-Fi. The player starts with a second of audio in hand instead of two and a half.

The same phone, the same tracks, the same Wi-Fi:

| | Before | After |
| --- | --- | --- |
| The track at the front of *Where you left off* | 6.5 s | 1.0 s |
| The next track in the queue | 6.5 s | 1.5 s |
| Any other track, app already open | 6.5 s | 2.3 s |
| Any other track, cold start | 6.5 s | 4.7 s |

The desktop keeps addresses the same way, so a replay and the previous button start at once there too.

## Repeat one, without the reload

Repeating a track used to mean fetching it all over again — a spinner and several seconds of nothing between the end and the beginning. Both players now loop the track themselves, with no gap and no request. Each time round still counts as a listen and is still scrobbled. A sleep timer set to *End of track* still ends the track: looping is lifted while one is set and comes back when it has gone off.

## "Unable to resolve host youtubei.googleapis.com"

That message came from a phone that had a perfectly good connection. Two things about it have changed.

A lookup that fails within the first few seconds for a network reason — the usual case is a phone changing networks at the wrong moment — is tried again, up to three times, before you are told anything.

When it still fails, what you are told comes from what the phone actually knows: that it has no connection, that it is on a Wi-Fi that leads nowhere, or that Spiceity in particular has been cut off by Data Saver while everything else on the phone is online. That last one has a fix, and it is in the phone's settings rather than in Spiceity, so it says so. The desktop's own wording for the same failure, from yt-dlp, is now recognised as well.

A stream that is refused partway through a track — usually an address issued on a network the phone has since left — is fetched afresh once and picked up at the same position, instead of stopping with a request to press play.

## Which file

| Platform | File |
| --- | --- |
| Windows | `Spiceity-0.3.4-windows-x64-setup.exe`, or the `.msi` for deployment |
| Debian, Ubuntu, Mint | `spiceity_0.3.4_amd64.deb` |
| Fedora, RHEL, openSUSE | `spiceity-0.3.4.x86_64.rpm` |
| Android | `Spiceity-0.3.4.apk` |

Windows packages carry mpv and yt-dlp inside them, so nothing has to be fetched before the first track plays. **Close Spiceity before installing** — the installer cannot replace files the running program holds open.

## Verifying a download

```
sha256sum --check --ignore-missing SHA256SUMS.txt
```

The APK is signed with Spiceity's release key, certificate fingerprint:

```
46:CF:8B:96:C4:37:49:7A:93:AF:76:2B:91:94:AD:11:09:5D:D6:4A:B6:AB:EA:E9:60:C0:A5:98:C5:63:49:ED
```

A debug-signed build already on a phone (from a `gradlew installDebug`) has to be uninstalled first; Android will not replace it with this one.

## Updating

Download it from this page. Spiceity's own updater cannot see this release: it asks GitHub's `/releases/latest`, which answers 404 for a private repository, and Spiceity reads that as being up to date.
